# Deployment

From nothing to a live study. Roughly 30–40 minutes the first time.

You do **not** need any of this to develop or test locally — `npm run dev` works on Node
alone. Do this when you are ready to collect real responses.

---

## What you are building

One Cloudflare Worker that serves both the participant-facing site and the server-side
logic, talking to one MongoDB Atlas cluster.

A Worker rather than Cloudflare Pages, because the MongoDB connection pool lives in a
Durable Object and Durable Object classes cannot be declared from Pages Functions. It is
a single deployment either way, and static files are served from the same place.

---

## Part 1 — MongoDB Atlas

### 1.1 Create the cluster

1. Sign up at [mongodb.com/cloud/atlas/register](https://www.mongodb.com/cloud/atlas/register).
2. Create a **free M0 cluster**. M0 is enough: 240 documents is nothing.
3. For the region, pick whichever is closest to your participants. Note which one — you
   will use it again in step 3.4.

### 1.2 Create a database user

Under **Database Access → Add New Database User**:

- Authentication: **Password**
- Give it a username and click **Autogenerate Secure Password**. **Copy the password
  now**; Atlas will not show it again.
- Role: **Read and write to any database**

### 1.3 Allow Cloudflare to connect

Under **Network Access → Add IP Address**, choose **Allow access from anywhere**
(`0.0.0.0/0`).

This is necessary rather than lazy: Workers run from Cloudflare's whole edge network and
have no fixed egress addresses to allow-list. Your database is still protected by the
username, the password and TLS. Use a strong autogenerated password and do not reuse it.

### 1.4 Get the connection string

**Database → Connect → Drivers → Node.js**. You will get something like:

```
mongodb+srv://myuser:<db_password>@cluster0.ab1cd.mongodb.net/?retryWrites=true&w=majority
```

Replace `<db_password>` with the real password. If the password contains any of
`@ : / ? # [ ] %`, it must be percent-encoded — the simplest fix is to regenerate a
password without them.

You do not need to create the database or the collections. They are created on first
write, and the indexes are built automatically on first connect.

## Part 2 — Cloudflare

### 2.1 Create the account

Sign up at [dash.cloudflare.com/sign-up](https://dash.cloudflare.com/sign-up).

The free plan is enough. Durable Objects with SQLite storage are included on it.

### 2.2 Log Wrangler in

```bash
npx wrangler login
```

This opens a browser to authorise. Then confirm:

```bash
npx wrangler whoami
```

## Part 3 — Configure and deploy

### 3.1 Generate your two secrets

Any long random strings. For example:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Run it twice — one value for `EMAIL_HASH_SALT`, one for `ADMIN_TOKEN`.

> **Keep the salt somewhere safe and never change it during data collection.** Every
> stored email hash is derived from it, so changing it makes them all unmatchable and
> duplicate control silently stops working.

### 3.2 Store the secrets in Cloudflare

```bash
npx wrangler secret put MONGODB_URI        # paste the Atlas string from 1.4
npx wrangler secret put EMAIL_HASH_SALT
npx wrangler secret put ADMIN_TOKEN
```

These are encrypted at rest and never appear in your repository. `.dev.vars` holds the
local equivalents and is git-ignored.

### 3.3 Make sure the images are extracted

```bash
npm run extract-assets
```

There should be 12 folders under `public/assets/combos/` plus a `manifest.json`.

### 3.4 Point the Durable Object at your Atlas region (optional, recommended)

In `src/index.js`, add a location hint matching the region you chose in 1.1:

```js
service: () => env.MONGO.get(env.MONGO.idFromName(DO_NAME), { locationHint: 'apac' })
```

Valid hints are `wnam`, `enam`, `sam`, `weur`, `eeur`, `apac`, `oc`, `afr`, `me`. This
keeps the Durable Object physically near the database, which is where the latency is.

### 3.5 Deploy

```bash
npm run deploy
```

Wrangler prints your URL, something like
`https://tshirt.<your-subdomain>.workers.dev`.

The Worker is named for the visible task only. That name is in the URL of every
participant's browser, so it must not name the construct under test — a participant who
searched the hypothesis before rating the garment would be answering a different
question than the one you asked.

### 3.6 Confirm it is talking to Atlas

```bash
curl -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  https://tshirt.YOUR-SUBDOMAIN.workers.dev/api/admin/health
```

You want `{"ok":true,"backend":"mongodb"}`.

If it says `durable-object-storage`, `MONGODB_URI` did not arrive — re-run 3.2 and
redeploy. **Do not collect data in that state**; responses would go into Durable Object
storage instead of your cluster.

### 3.7 Run the checks against the live deployment

```bash
node tools/self-check.mjs https://tshirt.YOUR-SUBDOMAIN.workers.dev
```

Two lines in its output matter as much as the pass count:

```
note: backend is "mongodb"
note: cell preview is absent (production)
```

The second confirms the development cell picker did not follow you into production. If it
ever says `ENABLED`, stop — participants could open any condition and level at will, and
the blinding is gone. You can check it directly too; a 404 is the correct answer:

```bash
curl -i -X POST https://tshirt.YOUR-SUBDOMAIN.workers.dev/api/dev/preview
```

Set `ADMIN_TOKEN` in your shell first, or the admin checks cannot authenticate:

```powershell
$env:ADMIN_TOKEN = "your admin token"
```

The two destructive admin checks — cleanup and delete-participants — are skipped against
a remote host unless you pass `--destructive-ok`. During collection they would delete
every part-way-through session and wipe duplicate control, silently, so the default is to
leave them out.

This writes a few dozen test sessions to your cluster. Clear them before going live:

```powershell
$env:MONGODB_URI = "mongodb+srv://..."
node tools/reset-study.mjs          # reports what is there, deletes nothing
node tools/reset-study.mjs --yes    # actually deletes it
```

Run it without `--yes` first and read the counts. It empties both collections, including
completed responses, which no admin endpoint can do — deliberately, since an HTTP route
able to delete completed responses is a route able to destroy the dataset.

Then confirm you are back to zero:

```bash
curl -H "Authorization: Bearer YOUR_ADMIN_TOKEN" .../api/admin/counts
```

## Part 4 — Before you recruit

Walk it yourself on a phone and a laptop, and check:

- [ ] Consent renders and declining ends without writing anything.
- [ ] A birth year of 1990 is refused with the right message; 1975 and 2000 are accepted.
- [ ] Both colour screens work. Tapping a swatch stamps "Locked" on it, tapping another
      moves the lock, and Continue is what commits the choice.
- [ ] On the second colour screen the colour you already used still shows "Locked" and
      cannot be picked again.
- [ ] The loading screen appears, then the reveal names your colour correctly, on two
      lines, with the attribution in brackets underneath.
- [ ] The garment renders in that colour.
- [ ] Whatever controls you were given actually change the shirt.
- [ ] All 8 questionnaire items must be answered before Submit works.
- [ ] After submitting, the back button cannot re-enter the study.
- [ ] `/api/admin/counts` shows your response in exactly one cell.
- [ ] Close the browser mid-task, reopen the URL, and confirm you return to the same
      stage with the same colour.

### Languages

The picker sits at the top of the consent screen and English is preselected. Walk the
study once in each language, on a phone, and check:

- [ ] Switching language on the consent screen redraws it immediately and keeps the
      consent checkbox ticked if it already was.
- [ ] Sinhala and Tamil render as text, not as empty boxes. If they do not, the device is
      missing both the system face and the downloaded one.
- [ ] The reveal sentence is in the chosen language and names the colour in it.
- [ ] Stage 4's controls are labelled in that language, and nothing overflows: the
      "Locked" badge inside a colour swatch and the three sleeve-length buttons are the
      tightest places and the first to break.
- [ ] Typing in Sinhala or Tamil into the custom text field prints readable text **on the
      shirt**, not boxes. The garment is drawn on a canvas with its own font, separate
      from the page.
- [ ] The exported CSV has a `language` column with the right value.

The local cell picker at `/preview` has a language dropdown, which is much faster than
walking the whole journey three times for each level.

**Do not recruit in Sinhala or Tamil until a native speaker has signed the translations
off.** `npm run strings` writes `exports/translations-for-review.csv` with every string
in all three languages and a column to correct each in. The eight questionnaire items and
the consent body are the ones that matter: they are a validated instrument and an ethics
document respectively, not interface copy.

If review is not finished when you want to start collecting, the safe move is to reduce
`LANGUAGES` in `public/shared/languages.js` to the entries that are approved. The picker
is built from that list, so removing one removes the option.

Then reset the collections one final time.

## While collecting

Check the balance periodically:

```bash
curl -H "Authorization: Bearer YOUR_ADMIN_TOKEN" .../api/admin/counts
```

Every few weeks, clear abandoned sessions (completed responses are never touched):

```bash
curl -X POST -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  -H "Content-Type: application/json" -d '{"olderThanDays":30}' \
  .../api/admin/cleanup
```

Watch for `flaggedFast: true` records — a Stage 4 under 15 seconds. They are saved
deliberately rather than blocked, so you can decide at analysis time whether to exclude
them.

### Exporting for analysis

```powershell
$env:ADMIN_TOKEN = "your admin token"
node tools/export-csv.mjs --url https://tshirt.YOUR-SUBDOMAIN.workers.dev
```

Writes `exports/responses.csv` — one row per completed participant, ready for SPSS, R,
JASP or Excel. It also prints the count per cell, so you can see your balance at a
glance, and flags how many responses were marked fast.

The flattening is the point. The stored document is not a rectangle: `customisation` is a
nested object whose keys depend on the assigned level, so the raw JSON gives you a column
that means different things in different rows. The CSV has a fixed set of columns for
everyone, blank where a control was never shown. **Blank means "not offered", not
"offered and not used"** — a Level 1 participant has no sleeve value because there was no
sleeve control, which is different from a Level 2 participant who left it alone. The
engagement flags are what distinguish the second case.

Booleans are written as 1/0 so SPSS reads them as numeric, and the file has a UTF-8 BOM
so Excel does not mangle non-ASCII custom text.

`exports/` is git-ignored. Participant data should not go into a repository even without
identifiers in it.

If you would rather have the raw JSON:

```bash
curl -H "Authorization: Bearer YOUR_ADMIN_TOKEN" .../api/admin/export > backup.json
node tools/export-csv.mjs --file backup.json
```

Only completed responses are ever returned, and they carry no email or hash.

### At the close of data collection

Delete the email hashes. The experimental data is unaffected because the two collections
share no key.

```bash
curl -X POST -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  .../api/admin/delete-participants
```

## Troubleshooting

**`backend` says `durable-object-storage`**
`MONGODB_URI` is not reaching the Worker. Re-run `wrangler secret put MONGODB_URI` and
redeploy. Nothing is being written to Atlas until this is fixed.

**Server selection timed out**
Network Access in Atlas is not set to `0.0.0.0/0` (step 1.3), or the cluster is paused.
Free clusters pause after long inactivity — resume it from the Atlas dashboard.

**Authentication failed**
The password in the connection string is wrong or contains characters needing
percent-encoding. Regenerate a password without `@ : / ? # [ ] %`.

Test a string locally before uploading it, rather than redeploying to find out:

```bash
# PowerShell
$env:MONGODB_URI = "mongodb+srv://..."
node tools/check-mongo.mjs
```

It checks the string for the usual mistakes before it tries anything, then connects,
authenticates, and proves write access by inserting and removing a test document. Each
failure comes with the specific thing to change in Atlas. The string is read from the
environment rather than an argument, so it stays out of your shell history.

**A secret was added but nothing changed**
Only affects `MONGODB_URI`, and only if a request arrived before you set it. The Durable
Object caches its Mongo connection for the life of the instance; the fallback to Durable
Object storage is deliberately *not* cached, so the switch happens on the next request.
If the health check still disagrees, `npm run deploy` restarts the instance.

**`npm run dev:workers` fails with `write EOF` or a missing DLL**
The Workers runtime needs the Microsoft Visual C++ Redistributable, which needs
administrator rights. Use `npm run dev` instead — it runs the same routes and the same
study logic on plain Node.

**A participant reports a blank screen after the reveal**
Almost always a missing image. Check `/assets/combos/manifest.json` loads and re-run
`npm run extract-assets`.

**Logs**

```bash
npx wrangler tail
```

Errors are logged without session ids or condition details, deliberately — a log is not
a place to put anything that could deanonymise a participant.
